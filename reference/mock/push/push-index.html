「消息推送」设置页：四套版面

四套只差下半区怎么分。上半区（总开关 + 触发事件 + 提醒内容）与下半区的内容完全相同： 一个服务可以挂多行具名主题（Bark 一串密钥一台设备，必须能加多行并起名）， ntfy 与 Bark 可同时启用，一次灯变会给所有启用服务下的每行主题各发一条。 ⚠️ 本页面是当初的选型对比，控件清单已按精简后的实现改过；只有方案 A 跟着更新，B / C / D 留作当时的思路记录。

方案 A · 双栏主从已实现

左列选服务（行内带各自开关 + 主题计数），右列管该服务的服务器地址与主题列表。下半区照抄「信息卡拓展」。

  • 与已有的「信息卡拓展 / 会话记录」完全同构，你不用重新学一套交互；实现上也能复用 .ep-panel 那套两栏 + 高度链
  • 两列各自滚，收件方再多也不撑长页面；破坏性操作（确认移除）就在行内，位置稳定
  • 服务数变多时，左列只是变长，不需要改版面
  • 一次只看一个服务，跨服务对比要来回点

方案 B · 服务卡并排 + 收件方宽表

上半区下面先来一排服务卡（开关 + 计数一目了然），整幅宽度给选中服务的收件方表格，字段行内直接改。

  • 设备多时最快：三台 iPhone/iPad/手表一屏看全，改完即存
  • 表格能放固定列（名称 / 地址 / 优先级 / 密钥 / 启用 / 操作），扫读成本最低
  • 行内输入框窄，长主题串会被截断（要看全文得悬停或展开）
  • 服务数一多，并排卡会挤成两行，形状开始不稳

方案 C · 纵向堆叠卡片（整页滚动）

不切栏：总开关在上，两个服务各一张卡，可分别展开/收起，收件方在卡内继续往下堆。

  • 窄窗口 / 高 DPI 下最稳，没有横向挤压问题
  • 两个服务能同时摊开对照着配（Bark 的设备与 ntfy 的主题并排看）
  • 收件方一多就要长距离滚动，「测试发送」按钮会跑出视区
  • 和同页其它两个 fill 面板的观感不一致（那两个是占满高度双栏自滚）

方案 D · 竖排服务栏 + 右列「配置 / 发送记录」

左列竖排服务（可滚、带开关圆点），右列拆两栏：收件方配置 + 最近发送记录（含失败原因与重试提示）。

  • 为「将来十几个 provider」准备：竖排可滚，服务名再长也不挤
  • 唯一把投递结果放进主视图的方案 —— 推送这类外部依赖，「为什么没收到」是最常见的问题
  • 三级信息密度最高，右列两栏在 1000px 宽下会比较紧（收件方表单列要缩到 2 列）
  • 竖排导航与主窗两级 tab 的横条语言不同，多了一种导航形状

四套共用的部分：provider 规范（已实现版）

版面只是外壳，真正决定「以后能不能再加 provider」的是下面这套数据模型与注册契约。 已选定方案 A，规范全文落在 reference/doc/agent-status-push-guide.md（本节是它的摘要）。 ⚠️ 首版实现之后按用户要求做过一轮精简：服务只剩「服务器地址」一个配置，收件方只剩「名字 + 主题」两列， 凭据管理器、优先级 / 铃声 / 分组、收件方开关、节流、静默、标题前缀、投递记录全部删除。 方案 B / C / D 的原样保留只为留下当时的对比依据，界面细节以 push-a-dual-pane.html 为准。

项约定
两层模型 provider（ntfy / bark / 将来更多）→ channel[]（该服务下的一行主题：id + name + topic，0..n 个）。 Bark 的多设备、ntfy 的多主题都是这一行 —— 设备密钥本身就是一个主题串，因此服务差异不需要特判，UI 也只有一套列表。 开关是与关系：总开关 ∧ 服务；主题行没有自己的开关。
配置存放 整体存在本模块的配置块 module_settings['agent-status'].push（外壳只透传、不解释字段）。 结构：{ enabled, events[], content[], providers: { ntfy: {enabled, server}, bark: {enabled, server} }, channels: [{id, provider, name, topic}] }。 ⚠️ 新增字段一律 optional + 默认值，不升 schema 版本（沿用本项目既有硬规则）；旧键（fields.server / fields.topic）仍读得出来，写回时整块替换自然消失。
加一个 provider = 两处登记 ① Rust：push/providers/<id>.rs 实现 PushProvider（id / label / server() / send()），在 build_providers() 加一行； ② 前端：lib/push-providers.ts 注册表加一行文案。不需要声明字段表，也不需要写新的 Vue 组件 —— 这与状态灯「加平台=加适配器」的收敛方式一致。
服务器地址 ServerSpec { label, default, help } 由 provider 自带：面板照它渲染一个地址输入框，留空 = 用官方默认。 校验只做 http(s):// + 形状 + 长度，允许局域网自建（与流程脚本的地址策略刻意不同）。
主题不是密钥 主题串明文显示、明文落配置（用户要的是看得见 + 能命名）。push 侧没有凭据管理器路径； flow 那边仍用自己的 KeyringSecrets。代价与旧版孤儿凭据见 guide §12。
触发与限流 事件源固定为内核已有的语义：TurnFinished / WaitingForUser / Failed / SessionFinished（灯已经会的东西，推送不再自造一套判定）。 一次灯变 → 该服务下每行主题各一条；不再节流、没有静默期。所有 agent 全停 = 零出网（与流程脚本同一不变量）。
投递与反馈 专用 worker 线程 + 串行队列 + 按主题行的指数退避（连续失败不每秒打网）；不再有内存投递记录，诊断入口是卡片右上角的统一测试： test_push_provider(provider_id) 逐主题回 {name, ok, status, error}。 UI 反馈一律 role="status" 行内提示，破坏性操作两步确认（本项目禁止 alert/confirm）。

方案 A 已实现并按精简要求改过一轮；契约、红线与验收清单以 reference/doc/agent-status-push-guide.md 为准 （命令两处：get_push_status 与 test_push_provider，都只在主窗授权）。
